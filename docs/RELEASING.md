# Release workflow maintenance

`dist-workspace.toml` is the source of truth for the release matrix, Linux build
dependencies and custom jobs. `.github/workflows/release.yml` is generated by the
pinned cargo-dist version (currently 0.32.0). Do not edit it directly or disable
its consistency check with `allow-dirty`.

After changing dist configuration or `.github/dist-build-setup.yml`, run:

```sh
dist generate --mode ci
dist generate --check
dist plan
```

The PR release workflow runs the plan and checks generated configuration without
publishing. Tag builds run the full pipeline:

1. dist selects the five supported platform/architecture targets.
2. The macOS build setup installs a pinned cargo-bundle and invokes
   `scripts/build_macos_dmg.sh` for each target. The script uses only that target's
   `Ropy.app`, creates a DMG with an Applications shortcut, and cleans temporary
   staging files even if image creation fails. It also creates
   `ropy-<target>-app.tar.xz` plus its SHA-256 sidecar from that complete app.
3. dist builds binary archives and SHA-256 sidecars for standalone installations.
   Installed macOS bundles use the `-app.tar.xz` payload, which updates resources
   and `Info.plist` together with the executable. DMGs remain manual downloads.
4. The `release-update-manifest.yml` reusable workflow runs after all local
   artifacts finish. It downloads both dist archives and complete macOS bundles,
   first requires the latest main CI run for the exact release commit to have
   completed successfully, then generates `latest.json` from the downloaded archives and
   the release plan, then uploads it as an `artifacts-*` workflow artifact. A
   missing archive or checksum fails this job and blocks release publication.
5. dist's generated host job collects all artifacts, including the DMGs and
   `latest.json`, and creates the GitHub Release. Custom jobs do not publish.

The DMG still uses cargo-bundle's release build, while dist uses its own dist
profile. This preserves the existing packaging behavior; this change does not
attempt to share binaries between the two build tools.

Run packaging regression tests without compiling or publishing:

```sh
python3 -m unittest discover -s scripts/tests -v
```

These tests cover architecture selection, staging cleanup, failure propagation,
and the updater manifest contract. They replace cargo-bundle and hdiutil with
fixtures; an actual macOS package build is still needed to validate the produced
application and disk image. `scripts/precheck.sh` also runs these tests.

## Update behavior and recovery

Automatic checks run at startup when due, then every 24 hours while Ropy is
running. The board samples the schedule every minute, including after resume.
Check timing and the selected channel are stored in `update-check.json` beside
`config.toml`. Failures retry after 15 minutes, doubling up to 24 hours; success
resets the backoff. Manual checks bypass timing. Disabling automatic checks is
respected by the next timer tick. A channel change invalidates a stale result.

Stable checks continue to use the release asset `latest.json` without the
GitHub API. Opting into prereleases queries the most recent 100 releases,
filters drafts and incompatible payloads, and selects the highest semantic
version. Turning prereleases off never downgrades an installed version.

Ropy detects standard Scoop, Homebrew prefix, Nix, Snap, Flatpak and system
binary paths as externally managed. These installations can check for releases
but cannot self-replace. Detection is conservative and path-based, not a universal
package receipt lookup. Publishers using another prefix can place `.ropy-managed`
next to the executable, or at `Ropy.app/Contents/.ropy-managed` for an app bundle.
They must preserve that marker in subsequent packages.

Downloads require HTTPS, their declared size and a valid SHA-256 sidecar. The
checksum verifies integrity, not publisher identity; release signatures are not
part of this update protocol. Archive entries and expanded size are bounded,
and symbolic links are rejected. The macOS payload must contain a complete
`Ropy.app`, including `Contents/Info.plist` and `Contents/MacOS/ropy`.

A verified payload is staged beside the installation in `.<filename>-update`
(for example `/Applications/.Ropy.app-update`). The metadata records the
installed version, downloaded version and original
executable SHA-256. A normal launch offers only a payload staged by the current
version for a newer release. Restart handoff and replacement also verify the
original executable fingerprint, rejecting a payload left behind by a manual
installation. Rejected payloads must be downloaded again. Legacy metadata can
still restore a backup from an interrupted transaction, but cannot install a
staged payload without provenance. No installed file is changed
until the user chooses to restart. The directory must be writable without
privilege escalation. A helper copied outside the target confirms readiness;
only then does the old application quit. The helper waits for the parent's
actual process exit, including release of the Windows single-instance mutex.

The helper moves the old installation to `backup`, installs the staged payload
on the same filesystem, and launches the new version. After its window and
repository initialize and the UI event loop runs for two seconds, the new
version acknowledges startup. The helper retains the backup until that
acknowledgment. If launch fails or no acknowledgment arrives within 45 seconds,
it stops the new process, restores the backup and launches the old version.
A rollback notice remains in About until the next manual check. A normal launch
also resumes an interrupted transaction when a backup exists and no helper
holds the transaction lock. An acknowledged healthy installation is never
rolled back merely because backup cleanup failed.

This recovers application files only. Future database format changes must remain
backward compatible with the prior version; the updater does not roll back
clipboard data. Unexpected helper errors are written to `helper.log` in the
transaction directory. If filesystem permissions prevent recovery, the `backup`
remains available for manual restoration. A power interruption between the two
renames can leave the installation path absent; restore the backup manually in
that case. The transaction directory and small metadata files are retained for
reuse; the old executable/bundle is removed after successful startup.

Old Ropy clients still use the binary-only archive contract. The first release
containing this updater installs through that existing path; subsequent updates
from a macOS bundle use full app payloads. Manual DMG installation also installs
the complete new bundle immediately.

## Updater verification

`cargo test --test update_handoff` runs the real updater helper against isolated
fixture processes. It checks that the parent is still usable before handoff,
that replacement waits for process exit, and that a failed startup restores and
launches the old executable. The fixture is compiled with the host `rustc` and
these tests run on macOS, Windows and Linux without accessing clipboard history.
Unit tests cover scheduling, selection, download bounds, staging and rollback;
GUI integration tests cover retry and managed-installation controls. The full
`scripts/precheck.sh` gate includes these tests.

Before publishing, smoke-test packaged upgrades on each platform, including a
read-only installation, a failed download, a successful restart and a failing
new executable. The process fixtures do not replace signed/notarized macOS
bundle validation or testing an actual Windows installation under antivirus.

## Workspace package selection

The root `ropy` package remains the sole release artifact. `ropy-core` is an
internal path dependency with `publish = false`, cargo-release `release = false`
and cargo-dist `dist = false`; its version is independent of the application.
`scripts/update_version.sh` selects `--package ropy`, and macOS bundling selects
the same package explicitly. Root application metadata, updater version lookup,
resource paths and archive names remain unchanged.

## Self-hosted Homebrew Cask

`StudentWeis/homebrew-tap` distributes `Casks/ropy.rb`. The initial Cask snapshot
is in `packaging/homebrew/ropy.rb`; the generator, not that snapshot, supplies
future versions. The stable GitHub Release DMGs remain the download source.

`.github/workflows/homebrew.yml` runs after the tag Release workflow succeeds, or
manually to retry synchronization. It uses `workflow_run` because releases
created with `GITHUB_TOKEN` do not trigger a second release-event workflow. It resolves the latest stable release,
reads GitHub-published SHA-256 digests for both DMGs and pushes the generated
Cask to the tap. Prereleases are excluded; missing artifacts or missing digests fail the job.
Homebrew verifies each downloaded DMG against that digest during installation.
The tap requires a write-enabled SSH deploy key; store its private key as the
Ropy repository secret `HOMEBREW_TAP_DEPLOY_KEY`. The regular `GITHUB_TOKEN` only
reads release assets. Do not use a personal access token for cross-repository
writes. Synchronization failure does not undo a published release; retry the
workflow after fixing the failure.

To regenerate a Cask locally:

```sh
gh release download 0.5.7 --repo StudentWeis/ropy --pattern 'ropy-*-apple-darwin.dmg' --dir /tmp/ropy-dmgs
python3 scripts/generate_homebrew_cask.py 0.5.7 /tmp/ropy-dmgs packaging/homebrew/ropy.rb
```

The Cask adds `Contents/.ropy-managed` after installing the app, including when
using a custom `--appdir`. This uses the existing updater ownership contract:
users can check releases in the app but install with `brew upgrade --cask ropy`.
Do not declare `auto_updates true`; Homebrew is responsible for upgrades.
Ordinary uninstall preserves clipboard history and configuration. No `zap` is
provided to avoid accidental deletion of clipboard data.

The current DMGs are unsigned. At the user's request, the self-hosted Cask runs
`/usr/bin/xattr -r -d com.apple.quarantine` against only the installed Ropy.app
after adding the managed marker. The install-time `{{appdir}}` token respects a
custom application directory. No sudo is used and other attributes are preserved.
Recursive deletion tolerates an absent quarantine attribute. Other command
errors stop installation and print the error. This does not sign or notarize the app and is specific to this
self-hosted tap; it is not suitable for an official Homebrew Cask submission.
Before introducing signed/notarized bundles, revisit the marker's
placement and verify it does not invalidate the bundle signature.

Validate syntax, style, download/unpacking and both architecture hashes. On a
machine without an existing Ropy installation, smoke-test installation, launch,
managed update behavior, upgrade/reinstall and uninstall before publishing
packaging changes. Never overwrite an existing app or clipboard data for tests.

## Protected release sequence

Prepare the version and changelog on a branch and merge them through a PR before
pushing a version tag. With cargo-release, use its preparation-only options:

```sh
scripts/update_version.sh <version> --execute --no-tag --no-push
```

After the preparation PR merges, wait for main CI to succeed. Tag the merged
commit (not the pre-squash branch commit). The release manifest job queries the
`ci.yml` workflow's push runs on main for that exact SHA, and accepts only the
latest run when completed successfully. Missing, running, cancelled, skipped or
failed runs block publication. API errors also fail closed. Once CI succeeds,
retry the failed Release jobs; do not move an existing published tag.

The check lives in the existing update-manifest job, so it adds no runner or
extra job. It runs after packaging and before publication. Generated Release
workflow changes must continue to come from cargo-dist configuration.

Complete [Release acceptance](RELEASE_ACCEPTANCE.md) against packaged artifacts.
The human GUI acceptance procedure is separate from the automated CI gate;
there is currently no GitHub environment approval enforcing that manual step.
